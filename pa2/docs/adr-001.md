# ADR-001 — Reliable RabbitMQ message delivery

**Status:** accepted
**Date:** 2026-09-16

## Context

The producer accepts HTTP requests and sends their JSON bodies to RabbitMQ for asynchronous processing. A `202 Accepted` response must not incorrectly tell the client that a message is safe when RabbitMQ has not confirmed it. Messages also need to survive a RabbitMQ restart and must not be lost if the consumer stops while processing them.

Each request has a correlation ID, either supplied through the `X-Correlation-Id` header or generated by the producer. That ID must travel from the HTTP request to the AMQP message properties and finally to the object written in `received.jsonl`, so a published message can be traced through the system.

## Decision

The producer creates a confirm channel in `connectProducerChannel` and declares the application queue with `durable: true`. In `publishMessage`, messages are published as persistent and include the request correlation ID in the AMQP `correlationId` property. In the default confirmed mode, the producer waits for RabbitMQ's publisher confirmation before returning `202 Accepted`; if confirmation fails, the request is not reported as successfully accepted.

The consumer declares the same durable queue in `connectConsumerChannel` and consumes with manual acknowledgement. In `handleMessage`, it reads `msg.properties.correlationId`, writes the message and correlation ID as one JSON object to `received.jsonl`, and only then acknowledges the message. If the consumer fails before the write and acknowledgement complete, RabbitMQ can redeliver the unacknowledged message.

## Alternatives considered

One alternative was to use a non-durable queue and non-persistent messages. This was rejected because messages still waiting in RabbitMQ could disappear after a broker restart.

Another alternative was fire-and-forget publishing, where the producer returns `202` immediately after calling `channel.publish()`. This was rejected as the default because the call only places the message in the client-side or network path; it does not prove that RabbitMQ accepted the message. Fire-and-forget remains useful as a demonstration mode, but it provides weaker delivery guarantees.

A third alternative was auto-acknowledgement or acknowledging before writing to `received.jsonl`. This was rejected because a consumer crash during the file write could lose the message permanently. Manual acknowledgement after the successful write provides at-least-once delivery instead.

## Consequences

Messages that were confirmed and persisted can remain available after RabbitMQ restarts, and messages can wait safely in the queue while the consumer is stopped. The correlation ID provides end-to-end traceability between the HTTP request, the queued message, and the JSONL output.

The system accepts additional latency because the producer waits for publisher confirmation, and it accepts the possibility of duplicate output if the consumer writes a record and crashes before acknowledging it. Consumers therefore need to treat messages as potentially redelivered and should make processing idempotent if duplicates are unacceptable.

If the consumer is slower than the producer, the durable queue can grow and consume broker memory or disk space. Multiple consumers can share work from the same queue, but message ordering across consumers is not guaranteed. Very large message bodies or a full RabbitMQ disk can also prevent publishing or confirmation, so production use would require message-size limits, monitoring, and capacity management.
