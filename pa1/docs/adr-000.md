# ADR-000 — Safe ingestion of legacy order exports

**Status:** accepted
**Date:** 2026-09-14

## Context

The integration receives two files from systems that use different formats and encodings. The orders file is fixed-width and encoded as Windows-1257, while the customer file is semicolon-separated CSV encoded as UTF-8. If the orders file is read as UTF-8, Latvian names such as Bērziņš can be decoded incorrectly without causing an error.

Each order record depends on exact column positions, because customer names can contain spaces. One record is shorter than the required 77 characters, so slicing it as if it were valid could create incorrect data. Amounts use comma decimals and may be negative refunds; converting them to JavaScript numbers can remove meaningful formatting such as trailing zeros.

## Decision

`ingest()` reads the orders export as bytes and decodes it using `decodeOrderFile()` with the `windows-1257` encoding. It splits the decoded text into non-empty lines and checks that every line is exactly 77 characters long. Invalid lines are added to `rejected` with their original line number, decoded raw value, and a reason; processing then continues for later records.

Valid order records are sliced using `ORDER_LAYOUT`, then trimmed. `toIsoDate()` changes the date by rearranging string parts rather than creating a `Date` object. `toDecimalString()` replaces the comma with a full stop while keeping the amount as a string, preserving trailing zeros and negative refunds. The customer CSV is read as UTF-8 and parsed into a map, then accepted order customer IDs are compared with the map keys to find unmatched customers.

## Alternatives considered

Using a library such as `iconv-lite` was considered for decoding, but it was rejected because `TextDecoder("windows-1257")` already provides the required decoding without adding a runtime dependency.

Splitting each order line on whitespace or using a regular expression was rejected because customer names contain spaces and the source contract defines exact column positions. Slicing by the fixed-width layout follows that contract directly.

Throwing an error when a record is malformed was rejected because it would stop the whole import and prevent valid orders after that line from being processed. Storing the bad record in `rejected` makes the data problem visible without silently losing valid records.

For a long-term integration, requesting a versioned JSON API or a documented structured file format from the upstream system would be preferable. However, this was not available for the current legacy export.

## Consequences

The importer now produces a usable report while preserving evidence of bad input. Valid orders continue to be processed after a malformed record, and rejected records include the line number, raw text, and reason for investigation. Keeping amounts as strings also preserves the exact value received from the source.

The cost is format coupling to the upstream export. If the upstream system inserts a field in the middle of the record, every following slice position becomes wrong and may produce plausible but incorrect data. If a customer name exceeds 32 characters, the upstream export may truncate the name or change the fixed-width layout, causing later fields to be read incorrectly.. If the orders file is changed from Windows-1257 to UTF-8, the configured decoder will produce incorrect names.

A longer-term solution should use a versioned and documented contract, such as a JSON API or a structured export with validation. Until then, the 77-character length check and rejected-record report provide basic protection, but they cannot detect every possible upstream format change.
