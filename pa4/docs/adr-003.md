ADR003 - Normalizing Orders and Enriching Prices

**Status:** accepted  
**Date:** 2026-10-12

## Context

The three input formats represent the same kind of order differently. The web source uses JSON product IDs directly. The mobile source uses shorter IDs, so `normalizeProductId` adds the `PROD-` prefix. The B2B XML uses `SKU-` prefixes, which the same helper removes. Mobile order dates are Unix epoch seconds, while the other sources provide date strings.

The B2B file uses Windows-1257 encoding. I decode its bytes before parsing the XML. XML parsing also requires handling a single `LineItem` differently from multiple items. The B2B `UnitListPrice` is not trusted for enrichment; prices come from the pricing API.

The inputs also contain payment details that do not belong in the canonical order. The pricing service can return an unknown-product response or an HTTP error, so the translator must handle failures without inventing a price.

## Decision

`normalizeProductId` converts the three source ID formats into the catalog IDs expected by the pricing service. `epochSecondsToIso` converts mobile timestamps to ISO date strings, and the source-specific status and currency helpers map input values to canonical values.

`enrichFromPricing` calls the pricing API for each product. `toDecimalAmount` uses `toFixed(2)`, so a price of `4.5` becomes the string `"4.50"`. A decimal string gives a consistent two-decimal representation for money.

`enrichItems` handles each line separately. A 404 creates an `UNKNOWN_PRODUCT` warning, and a pricing API error creates a `PRICING_API_ERROR` warning. The affected item is dropped, but other successfully priced items can remain. If no items can be priced, the translator returns no order and the warnings rather than making up a price such as `"0.00"`.

Each translator copies only the customer and order fields needed by the canonical model. It does not copy payment fields from the web, mobile, or B2B input. B2B prices are obtained from the pricing service rather than `UnitListPrice`.

## Alternatives considered

One alternative was to store prices as integer cents. That can avoid some floating-point problems, but the canonical model expects a decimal string, so it would require conversion before output. I chose `toFixed(2)` to match the expected representation.

Another option was to reject the entire order if one product could not be priced. I chose to drop only the unpriceable item and record a warning, because other valid items can still be processed. I also chose not to cache prices: calling the API for each item keeps the result up to date, but costs more requests and makes processing dependent on service availability.

## Consequences

The translators keep source-specific conversion separate from pricing enrichment, and payment details are not copied into the output. The main cost is that an order can lose items when pricing fails, so warnings must be checked rather than ignored.

If the canonical schema gains a required field, the translators may stop producing valid orders until the field is mapped. If a fourth source uses a new product-ID format, `normalizeProductId` needs another explicit rule. If traffic increases tenfold, repeated pricing requests are likely to become a bottleneck before the simple field mappings do. Caching could reduce requests, but it would introduce stale-price and invalidation problems.
