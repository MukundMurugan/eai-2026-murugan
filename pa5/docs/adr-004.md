# ADR-004 — Per-Consumer Retry Routing and Durable Notification Deduplication

**Status:** Accepted  
**Date:** 2026-10-26

## Context

PA5 requires payment, inventory, and notification to process an order independently. A temporary failure must not immediately discard a message, and retrying one consumer must not cause the other consumers to process the order again. Messages also need a correlation identifier so that results from the three services can be traced to the same submitted order.

The canonical order schema does not allow extra fields. Therefore, the correlation identifier belongs in AMQP message metadata rather than in the order body. The notification service also needs to handle at-least-once delivery without writing duplicate notification records.

## Decision

The order service generates a UUID v4 correlation identifier for each accepted request. It publishes the original order body to `orders.exchange` with the identifier in the `correlationId` header and with persistent delivery enabled. It stores the order by correlation identifier so that `GET /orders/:correlationId` can retrieve it.

The consumers use the fanout exchange for independent processing. Temporary simulated failures follow the existing TTL-based retry path. After three failed attempts, the message is sent to `orders.dlq.exchange`. Invalid JSON is classified as a permanent failure and routed to `orders.invalid.exchange` without retrying it.

The dead-letter and invalid-message exchanges and queues are durable fanout resources. They use the same declarations in each service to avoid inconsistent RabbitMQ topology.

For replay, the order service reads messages from `orders.dlq`, uses the `originQueue` header to identify the consumer that failed, and publishes to `orders.return.exchange` with that queue as the routing key. It removes retry history before republishing so the message can receive a fresh set of attempts.

The notification service stores processed correlation identifiers in `/data/processed-ids.json`. If an identifier is already present, it acknowledges the duplicate without appending another notification record. Otherwise, it writes the notification, persists the identifier, acknowledges the message, and publishes the result.

## Alternatives considered

One alternative was to place the correlation identifier in AMQP's native `properties.correlationId` field rather than in a custom header. The implementation uses the `correlationId` header, so producers and consumers must consistently read and forward that header.

Another alternative was an in-memory `Set` for notification deduplication. A `Set` would be simpler, but restarting the container would erase its history and could allow a previously processed order to produce another notification. A file preserves the identifiers across ordinary service restarts.

A further alternative was to retry through the original fanout exchange. That would send a failed message to all three consumers again. Returning the message to its original queue avoids unnecessary duplicate work in the other services.

## Consequences

Per-consumer retry routing isolates failures and prevents one consumer's retry from automatically repeating work in the other consumers. The cost is duplicated retry and error-handling code in the services, which must remain consistent.

The file-based deduplication store survives ordinary container restarts when its data directory is persisted. However, two notification-service replicas sharing the same file could race while reading and updating it; the file is not a transactional distributed deduplication store.

If a consumer fails more than the configured retry limit, its message reaches the dead-letter queue and requires investigation or replay. This bounds automatic retries, but a downstream service that remains unavailable beyond the retry window can still require human intervention.
