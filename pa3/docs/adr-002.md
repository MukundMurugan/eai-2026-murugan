# ADR-002 — Correlated Order Aggregation and Idle Timeout
**Status:** Accepted
**Date:** 2026-10-02

## Context

The order router splits an order into independent item messages. Physical, digital, and subscription workers process those messages separately and publish their results to `orders.results`. The aggregator must combine results for each order without mixing concurrent orders, counting duplicates twice, or waiting indefinitely when a worker fails to respond.

The main trade-off is between waiting long enough for slow items and returning partial results promptly when an item never responds.

## Decision

### Correlation and isolation

The router preserves `orderId` and `correlationId` in every item message. It also adds `itemIndex` and `totalItems`. The aggregator groups results by `orderId` and stores each result under its `itemIndex`, so concurrent orders have separate aggregation state.

The correlation ID must remain consistent throughout the pipeline. If a worker removes or renames it, the aggregator can no longer reliably preserve the original correlation information.

### Idle timeout

The aggregator uses `AGGREGATOR_IDLE_TIMEOUT_SECONDS`, defaulting to 5 seconds in Docker Compose. A background thread checks for orders that have received no new distinct item result within this interval. The timeout is refreshed when a new item result arrives.

Five seconds is the assignment's test configuration, not a validated production value. In production, I would measure worker response-time distributions, broker delays, and timeout frequency under representative loads, then choose a timeout that accommodates normal latency without delaying partial responses unnecessarily.

An idle timeout is preferable to a fixed deadline from order creation because larger orders may need more time. Each new result demonstrates progress and resets the idle interval.

### Complete and partial results

When all distinct item results arrive, the aggregator publishes one message with `status: "complete"` and an empty `missingItemIndexes` list.

If the order becomes idle before all results arrive, it publishes a partial message containing the results received so far, `receivedItems`, and the exact missing item indexes. This lets downstream consumers identify which items still need attention rather than treating the entire order as a total failure.

### Duplicate handling

The aggregator stores results in a dictionary keyed by `itemIndex`. A repeated result for the same index does not increase the result count or replace the first result. Completed order IDs are also tracked so that late results do not start a second aggregation during the process lifetime.

Malformed result messages are logged and acknowledged so they do not permanently block the results queue.

Unknown item types are logged and routed to `orders.physical` as a fallback, preventing them from silently disappearing. This is a pragmatic assignment choice; a production system should consider a dedicated error or dead-letter queue.

## Alternatives considered

- **Fixed deadline from order creation:** Rejected because larger orders and slower workers could be marked partial despite continuing to make progress.
- **Redis or another persistent store:** Not selected for this assignment because an in-memory dictionary is simpler and requires no additional service. Persistent storage would be more suitable if aggregation state must survive restarts.
- **Count every result message:** Rejected because RabbitMQ redelivery could cause duplicate item results to be counted twice. Keying results by `itemIndex` makes duplicates idempotent.
- **Route unknown types to an error queue:** Not implemented because the supplied architecture does not include one. A dedicated error queue would provide clearer failure handling in production.

## Consequences

The implementation supports independent orders, duplicate detection, complete results, and partial results after an idle period. The timeout sweeper performs state changes under a lock and publishes completion messages outside the lock to avoid holding the lock during network I/O.

The design has limitations. Aggregation state and completed-order IDs are held in memory and are lost if the aggregator restarts. A restart during an order can therefore prevent correct aggregation of that order. The completed-order set also grows over time. At higher traffic volumes, persistent state, bounded retention, and reliable publication with retry or transactional handling would be needed.
